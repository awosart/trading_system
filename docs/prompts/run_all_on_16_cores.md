# Промпт: полный прогон каталога стратегий на второй машине (16 ядер)

Отдать этот файл Клоду на второй машине. Всё, что ниже, измерено на первой
машине (8 ядер, Mac14,7) — не оценено. Если твои замеры разойдутся с этими,
скажи об этом, а не подгоняй.

---

## 0. Что это за задача и чем она не является

Прогнать **815 нормализованных стратегий** по всем инструментам, которые каждая
из них допускает, собрать каталог и **сохранить полные прогоны только для тех,
у кого максимальная просадка меньше 10%**. Остальные посчитать и назвать
числом, а не выбросить молча.

**Это разведка, а не свидетельство.** Один период, параметры из файла стратегии,
без фолдов, без подбора, без нулевых процессов. Хорошая строка означает ровно
одно — «эту стратегию стоит прогнать через walk-forward», и никогда «эта
стратегия работает».

**Отдельно и важно: holdout уже израсходован.** Последние 20% каждой ленты были
отрезаны до всех прогонов, использованы один раз для подтверждения 29
кандидатов (результат: 0 из 29) и больше не используются ни для чего. Скрин
режет ленту той же функцией и работает по первым 80% — это структурная
гарантия, а не договорённость, и её проверяет тест обходом графа объектов.
**Ничего из того, что ты получишь, подтвердить уже нечем.** Каталог — это
каталог.

---

## 1. Что должно приехать на машину

Три каталога вне git, без них ничего не запустится:

| путь | размер | обязателен | зачем |
|---|---|---|---|
| `data/` | 142 МБ | **да** | стор parquet, 11 символов × до 7 TF |
| `strategies/test_strategies/` | 7.3 МБ | **да** | 815 спек + `manifest.json` |
| `strategies/scraped_strategies_v3/` | 3.9 МБ | нет | только если пересобирать спеки |
| `runs/` | 204 МБ | **нет, не копируй** | результаты прежних этапов; см. §5 |

Всё остальное — под git.

```bash
make install                                   # bootstrap uv + uv sync -> .venv
.venv/bin/ts data coverage --symbol EURUSD --timeframe H4   # стор доехал?
.venv/bin/python -m pytest -q                  # ожидается 3104 passed
```

Если тестов меньше или есть падения — **остановись и скажи**, дальше не иди:
прогон на изменённом дереве даст числа, не сравнимые с записанными здесь.

## 2. Команда

```bash
scripts/run_all.sh 16 0.10 20000
```

Три аргумента: воркеров, порог просадки, баров на задачу. Скрипт проверит
предусловия, запустит скрин и построит индекс.

Эквивалент напрямую, если нужно менять что-то ещё:

```bash
.venv/bin/ts strategy screen strategies/test_strategies/specs \
  --symbols 0 --workers 16 --bars 20000 \
  --keep-max-dd 0.10 --returns-sample 200 \
  --out reports/screen_all.html
.venv/bin/ts report index --out reports/runs/index.html
```

### Выбор охвата — реши и скажи, что выбрал

Стоимость строго линейна по числу задач. Измерено: 36 860 воркер-секунд на
полную матрицу, эффективная параллельность 7.9× на 8 воркерах.

| `--symbols` | задач | 16 ядер (оценка) |
|---|---|---|
| `0` — все допустимые | 7 776 | **~47 мин** |
| `3` — три дешёвых по издержкам рынка | 2 445 | ~15 мин |
| `1` | 815 | ~5 мин |

По умолчанию `0`. `3` даёт результат, напрямую сравнимый с предыдущими этапами
(они гонялись именно так), и не добавляет 5 300 задач в знаменатель поправки на
множественное тестирование.

**H1 и H4 съедают 83% времени** (5 080 задач, у H4 медиана 896 сделок на
прогон). Отбрасывать M1/M5 бессмысленно — это 8% времени.

## 3. Чего ждать по числам

Из прогона 2 445 задач на первой машине:

- завершатся ~98%; **упадут около 2%** — почти все с `ValueError` про дневной
  якорь на индексах и товарах (у них свой торговый день, FX-календарь не
  подходит). Это свойство данных, а не дефект скрина;
- **торговать будут ~82%**, остальные не найдут ни одного сетапа;
- **фильтр просадки пропустит ~1.7%** от торговавших. На полной матрице это
  примерно **110 сохранённых прогонов из 7 776**, около 6 МБ на диске вместо
  400 МБ. Если у тебя получится радикально другая доля — это находка, скажи;
- медианная просадка среди торговавших — **33.9%** при риске 1% на сделку.

**Просадка почти линейна по риску.** `max_dd < 10%` при `--risk 0.01` — это
примерно `max_dd < 20%` при 0.005. Фильтр есть совместное утверждение о
стратегии и о сайзинге, не о стратегии одной, и в отчёте это должно быть
сказано.

## 4. Грабли, на которые я уже наступил

1. **Вывод буферизуется, если stdout не терминал.** Прогресс не видно.
   Смотри `wc -l runs/sweep/*/rows.jsonl` — строки дописываются по мере
   готовности.
2. **Прогон возобновляемый.** Прервать можно в любой момент: потеряется одна
   задача, повторный запуск той же команды продолжит с места остановки.
   Проверено — я терял так 25-минутный прогон и восстанавливал за секунды.
3. **`screen_id` считается от `source_digest`.** Любая правка любого `.py`
   даёт новый id, и прогон начнётся заново. **Не правь код во время прогона.**
   Я потерял так два полных прогона по 25 минут.
4. **Просадка хранится со знаком** (медиана −0.339). Фильтр сравнивает модуль.
   Если будешь считать что-то своё по `rows.parquet` — не забудь `abs()`.
5. **`ts report index` обходит весь `runs/`.** Если каталог не пустой, в индекс
   попадут и чужие прогоны. Поэтому `runs/` копировать не надо.
6. **Не запускай ничего на holdout.** Ни `validate verdict`, ни повторный
   `confirm`. Он потрачен; см. CLAUDE.md, «Решения P22 этап 3».

## 5. Что отдать обратно

Коротко, числами:

1. Фактическое время против оценки (47 мин на `--symbols 0`). Если разошлось
   больше чем на 30% — скажи, что оказалось горячим.
2. Сколько задач: запланировано / завершилось / торговало / упало, и топ-3
   причины падений.
3. **Сколько прошло фильтр просадки и сколько не прошло** — это то, ради чего
   всё затевалось.
4. Разбивка прошедших по таймфрейму и инструменту. На первой машине из 34
   прошедших 16 были M1 и 10 M5, то есть там, где издержки съедают ожидание, —
   низкая просадка там чаще означает «почти не торговала», а не «устойчива».
   Проверь, повторилось ли.
5. Пути: `reports/screen_all.html`, `reports/runs/index.html`,
   `runs/sweep/{id}/rows.parquet`.
6. Одна строка про то, чем этот каталог не является — см. §0. Без неё верхние
   строки прочитают как результат.

---

## 6. Что НЕ делать

- Не менять пороги после того, как виден хоть один результат.
- Не трогать holdout.
- Не оптимизировать код «по дороге» — см. грабли 3.
- Не запускать walk-forward или вердикт: это следующий этап, и он требует
  данных, которых пока нет.
- Не ставить `APPROVED` ничему: гейт на вердикт `ROBUST`, и его никто не
  проходил.

## 7. Если что-то пойдёт не так

Всё, что падает, падает **в строку с причиной**, а не роняет прогон: одна
сломанная спека среди тысяч не должна стоить остальных. Если упал сам раннер —
`rows.jsonl` цел, продолжай той же командой.

Если предусловие не выполнено (нет `.venv`, нет `data/`, нет спек) — скрипт
скажет, чего именно не хватает, и выйдет с кодом 1.
